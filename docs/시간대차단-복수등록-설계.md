# 예외일 "시간대 차단" 복수 등록 — 구현 명세

일산 이주희 팀장 요청: 같은 날짜에 시간대 차단을 여러 건 등록.
대상 저장소: `teemartbottle/maria-reservation`, `teemartbottle/maria-reservation-rpc` (평촌)

---

## 1. 현상과 원인

원장님이 하루에 두 번째 시간대를 저장하면 첫 번째가 사라진다.

원인 두 가지가 겹쳐 있다.

1. **저장이 덮어쓰기다.**
   `prisma/schema.prisma` 의 `ScheduleException` 에 `@@unique([doctorId, date])` 가 있고,
   `app/api/admin/schedule-exceptions/route.ts` 의 POST 가
   `upsert({ where: { doctorId_date: { doctorId, date } } })` 로 저장한다.
   같은 날짜 두 번째 저장은 새 행이 아니라 기존 행의 갱신이 된다.

2. **한 행이 시간 구간을 하나만 담는다.**
   `ScheduleException` 에는 `customStart` / `customEnd` 한 쌍뿐이다.
   유니크 제약을 풀어 행을 여러 개 만드는 방식은 `endDate` 범위 저장 로직과
   upsert 가 모두 "날짜당 한 행" 전제 위에 있어 함께 깨진다.

## 2. 운영의 현재 시간대 차단 경로

`ScheduleTemplate.slotSettings` (String? @db.Text) 에 JSON 으로 들어간다.

```json
{ "defaultCapacity": 1, "customSlots": { "14:00": { "type": "OFF", "capacity": 0 } } }
```

`lib/reservation/slotCalculator.ts` 가 이를 파싱해 `configMap` 으로 펼치고,
`type: 'OFF'` 인 슬롯을 막는다. 쓰기는 `app/api/admin/schedule-manager/route.ts`.

한계: **요일 단위이고 영구다.** 특정 날짜만 막을 수 없다.

`DoctorBlockedTime` 모델은 스키마에 존재하지만 슬롯 계산이 읽지 않는다(죽은 테이블).
이 테이블을 되살리는 방식은 차단 경로를 둘로 쪼개므로 채택하지 않는다.

## 3. 채택 설계

`ScheduleException` 에 `slotOverrides` 컬럼을 추가한다.
값의 모양은 기존 `customSlots` 와 동일하게 맞춘다.
`type` 에 `BLOCK` 을 추가한다 — "그날은 평소 템플릿대로 하되 `slotOverrides` 의 시간만 뺀다".

```prisma
model ScheduleException {
  // ... 기존 필드 유지
  slotOverrides String? @db.Text  // { "14:00": { "type": "OFF", "capacity": 0 }, ... }
}
```

병합 우선순위: `defaultCapacity` → 템플릿 `customSlots` → 예외일 `slotOverrides`.

채택 이유:
- 새 테이블 없음. 차단 개념은 `customSlots` 하나로 유지.
- 유니크 제약을 건드리지 않음 → `upsert` 와 `endDate` 범위 로직 보존.
- 시간이 map 이라 같은 날짜 복수 구간이 구조적으로 가능.
- 슬롯 계산의 병합 지점이 `configMap` 생성 직후 한 곳.

## 4. 변경 파일

1. `prisma/schema.prisma`
   `ScheduleException` 에 `slotOverrides String? @db.Text` 추가 + 마이그레이션.
   기존 행은 NULL → 동작 변화 없음.

2. `lib/reservation/slotCalculator.ts`
   `customSlots` 를 `configMap` 에 적용한 직후, 해당 날짜 예외일의 `slotOverrides` 를
   파싱해 같은 `configMap` 에 덮어쓴다. (현재 파일 188행 부근)

3. `lib/slots/precompute.ts`
   `DailySlotSummary` 사전 계산에도 동일한 병합을 적용.
   누락되면 달력의 잔여 수치가 실제 슬롯과 어긋난다.

4. `app/api/patient/slots/count-by-date/route.ts`
   주석에 "slotSettings의 customSlots 정확히 반영" 이라 되어 있다.
   여기도 동일 병합 필요. 누락 시 달력 숫자와 상세 화면이 불일치.

5. `app/api/admin/schedule-exceptions/route.ts`
   POST 에서 `type === 'BLOCK'` 이면 body 의 구간 배열
   `[{ startTime, endTime }, ...]` 을 그날 템플릿의 `slotIntervalMinutes` 로 펼쳐
   `slotOverrides` JSON 을 만든다. 기존 `invalidateSlotCache` / `updateSlotSummary`
   호출 경로를 그대로 탄다.

6. `app/(admin)/admin/schedule-exceptions/page.tsx`
   유형에 "시간대 차단" 추가. 구간을 여러 개 넣을 수 있는 입력
   (시작/종료 한 쌍 + "구간 추가" 버튼 + 각 행 삭제).
   목록에서는 차단된 구간들을 한 줄로 요약해 보여준다.

## 5. 반드시 처리할 것

- **이미 잡힌 예약**: 차단해도 기존 예약은 사라지지 않는다. 저장 시 해당 구간의
  활성 예약(PENDING, BOOKED) 건수를 세어 "이 구간에 예약 N건이 있습니다" 를
  경고로 띄운다. 없으면 원장님은 막았다고 알고 있는데 환자가 온다.
- **슬롯 간격**: 구간을 시각 목록으로 펼칠 때 그날 적용되는 템플릿의
  `slotIntervalMinutes` 를 사용한다. 하드코딩 금지.
- **경계**: `[시작, 종료)` 반개구간으로 통일. 14:00–15:00 차단 시 15:00 은 살아 있다.
- **연속 날짜**: `BLOCK` 은 우선 단일 날짜만 지원한다. `endDate` 범위와의 조합은
  범위 전체에 같은 시간대를 적용하는 의미가 되어 별도 합의가 필요하다.
- **평촌**: `maria-reservation-rpc` 에 동일 적용.

## 6. 검증

- 같은 날짜에 오전/오후 두 구간을 등록 → 둘 다 남아 있고 둘 다 예약 화면에서 사라진다.
- 차단 구간 경계 시각이 반개구간 규칙대로 동작한다.
- 달력의 잔여 건수, 날짜별 카운트 API, 예약 상세 슬롯이 서로 일치한다.
- 차단 후 삭제하면 슬롯이 되살아난다.
- 기존 OFF / CUSTOM 예외일 동작에 변화가 없다.
